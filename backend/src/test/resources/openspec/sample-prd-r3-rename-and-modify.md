## 1. 문제 정의

CMP에서 클라우드 플랫폼(AWS, K8s, vSphere, NCP, OpenStack, Contrabass 등)의 권한과 업무 라벨의 권한이 서로 충돌하고 있다.

- 챗봇에서는 거버넌스상 업무 라벨이 할당된 자원만 보여야 한다.
- 그러나 클라우드 플랫폼은 개발 당시 업무 라벨이 고려되지 않았다. 그래서 클라우드 플랫폼의 자원 데이터에서는 업무 라벨 할당 여부를 식별하기 어렵다.
- 두 권한 체계가 모두 존중되어야 하므로, 한쪽을 다른 쪽으로 대체하는 방식으로는 해결할 수 없다.

## 2. 목표

- 클라우드 플랫폼에서 보이는 데이터에서 업무 라벨을 식별할 수 있게 한다. 모든 플랫폼에서 식별 가능해야 하며, 식별할 수 없는 플랫폼이 없어야 한다.
- 업무 라벨에 따라 클라우드 플랫폼의 자원을 조회(필터링)할 수 있게 한다.
- 업무 라벨이 할당되지 않은 자원만 조회할 수 있게 한다. (백엔드 기능)
- 라벨 기준 조회, 미할당 조회, 전체 조회를 모두 할 수 있게 한다.
- 챗봇이 `/api/inventory` 하위 API로 조회할 때 업무 라벨이 할당된 자원만 노출되도록 한다.
- 위 항목을 화면 표시와 백엔드 기능 개선으로 달성한다.
- 개발(dev) 환경에 먼저 구현하고, 이후 운영(prd) 환경에도 적용한다.

## 3. 비목표

- 클라우드 플랫폼 권한 모델과 업무 라벨 권한 모델의 통합. 당장은 불가능하며 이번 범위에서 하지 않는다.
- 두 권한 중 한쪽을 우선시하도록 권한 판정 규칙을 바꾸는 것. 두 권한 모두 기존대로 존중한다.
- 업무 라벨 미할당 자원 조회를 위한 화면(UI). 백엔드 기능만 제공한다.
- 챗봇이 호출하는 `/api/inventory` 하위 외의 API.

## 4. 승인 기준 (Acceptance Criteria)

용어: "일반 조회"는 챗봇이 아닌 경로(화면, 직접 API 호출)의 `/api/inventory` 하위 조회를 말한다. 챗봇 조회는 AC-6과 AC-10을 따르며 AC-3, AC-4, AC-5는 적용하지 않는다.

### AC-1: 업무 라벨 할당 여부 표시
시스템은 클라우드 플랫폼에서 보이는 자원 각각에 업무 라벨 할당 여부를 공통 컴포넌트 기준으로 표시해야 한다(SHALL).

#### 시나리오: 라벨이 할당된 자원 표시
- 조건: 업무 라벨이 할당된 자원이 있다
- 동작: 사용자가 클라우드 자원 탭을 연다
- 결과: 해당 자원에 업무 라벨 할당 표시가 공통 컴포넌트로 나타난다

#### 시나리오: 라벨이 없는 자원 표시
- 조건: 업무 라벨이 하나도 할당되지 않은 자원이 있다
- 동작: 사용자가 클라우드 자원 탭을 연다
- 결과: 해당 자원은 미할당 상태로 표시된다

### AC-2: 업무 라벨 OR 필터
일반 조회에서 업무 라벨을 하나 이상 지정하면, 시스템은 지정한 라벨 중 하나라도 할당된 자원만 결과에 포함해야 한다(SHALL). 여러 라벨은 OR 조건이다.

#### 시나리오: 여러 라벨 OR 조회
- 조건: 자원 A에는 라벨 L1, 자원 B에는 라벨 L2, 자원 C에는 라벨이 없다
- 동작: 일반 조회에서 라벨 L1, L2를 지정한다
- 결과: 결과에 A와 B가 포함되고 C는 포함되지 않는다

### AC-3: 업무 라벨 미할당 조회
일반 조회에서 미할당 조회를 요청하면, 시스템은 업무 라벨이 하나도 할당되지 않은 자원만 결과에 포함해야 한다(SHALL). 이 조회는 백엔드 API로만 제공하며 화면에는 노출하지 않는다.

#### 시나리오: 미할당 자원만 조회
- 조건: 라벨이 할당된 자원 A와 미할당 자원 C가 있다
- 동작: 일반 조회 API로 미할당 조회를 요청한다
- 결과: 결과에는 C만 포함된다

#### 시나리오: 화면에 미할당 조회 없음
- 동작: 사용자가 클라우드 자원 탭의 필터를 연다
- 결과: 미할당 조회 선택지는 보이지 않는다

### AC-4: 라벨 지정과 미할당 동시 조회
일반 조회에서 라벨 지정과 미할당 조회를 함께 요청하면, 시스템은 지정한 라벨이 할당된 자원과 미할당 자원을 모두 결과에 포함해야 한다(SHALL).

#### 시나리오: 라벨 L1과 미할당 동시 조회
- 조건: 자원 A에는 L1, 자원 B에는 L2, 자원 C에는 라벨이 없다
- 동작: 일반 조회에서 L1과 미할당 조회를 함께 요청한다
- 결과: 결과에 A와 C가 포함되고 B는 포함되지 않는다

### AC-5: 라벨 필터 없는 전체 조회
일반 조회에서 업무 라벨을 지정하지 않으면, 시스템은 업무 라벨 필터 없이 전체 자원을 조회해야 한다(SHALL).

#### 시나리오: 필터 없는 조회
- 동작: 일반 조회에서 라벨과 미할당 조건 없이 조회한다
- 결과: 라벨 할당 여부와 관계없이 조회 권한이 있는 전체 자원이 결과에 포함된다

### AC-6: 챗봇 조회는 라벨 할당 자원만 반환
챗봇이 `/api/inventory` 하위 API로 자원을 조회하면, 시스템은 요청 조건과 관계없이 업무 라벨이 할당된 자원만 응답에 포함해야 한다(SHALL).

#### 시나리오: 챗봇 일반 조회
- 조건: 라벨이 할당된 자원 A와 미할당 자원 C가 있다
- 동작: 챗봇이 `/api/inventory` 하위 API로 조회한다
- 결과: 응답에 A만 포함된다

#### 시나리오: 챗봇이 미할당 조회를 요청
- 동작: 챗봇이 미할당 조회 조건을 붙여 조회한다
- 결과: 미할당 자원은 반환되지 않는다

### AC-7: 조회 권한 없는 자원 제외
시스템은 사용자에게 조회 권한이 없는 자원을 일반 조회 결과에 포함하지 않아야 한다(MUST NOT).

#### 시나리오: 권한 없는 라벨 자원
- 조건: 사용자에게 자원 D의 조회 권한이 없고 D에는 L1이 할당되어 있다
- 동작: 일반 조회에서 L1을 지정한다
- 결과: 결과에 D는 포함되지 않는다

### AC-8: 존재하지 않는 라벨 무시
일반 조회에서 존재하지 않는 업무 라벨을 지정하면, 시스템은 400 오류를 반환해야 한다(SHALL).

#### 시나리오: 없는 라벨과 있는 라벨 함께 지정
- 조건: 라벨 L1은 존재하고 라벨 X는 존재하지 않는다
- 동작: 일반 조회에서 L1과 X를 지정한다
- 결과: 400 오류가 반환된다

#### 시나리오: 없는 라벨만 지정
- 동작: 일반 조회에서 존재하지 않는 라벨 X만 지정한다
- 결과: 400 오류가 반환된다

### AC-10: 챗봇 조회의 권한 존중
시스템은 사용자에게 조회 권한이 없는 자원을 챗봇 조회 응답에 포함하지 않아야 한다(MUST NOT).

#### 시나리오: 권한 없는 라벨 자원
- 조건: 사용자에게 자원 D의 조회 권한이 없고 D에는 업무 라벨이 할당되어 있다
- 동작: 챗봇이 그 사용자로 조회한다
- 결과: 응답에 D는 포함되지 않는다

### AC-11: 라벨 필터 응답 시간
일반 조회에서 라벨 필터를 지정한 조회는 자원 1만 건 기준 2초 안에 응답해야 한다(SHALL).

#### 시나리오: 1만 건 조회
- 조건: 지원 플랫폼 자원이 1만 건 있다
- 동작: 일반 조회에서 L1을 지정한다
- 결과: 2초 안에 응답한다

### 승인 기준 명확성 점검

- [x] 모든 AC에 시나리오가 하나 이상 있고, 각 시나리오에 동작과 결과가 있다
- [x] 실패·예외 경로(권한 없음, 잘못된 상태, 빈 입력)에 대한 시나리오가 있다
- [x] AC끼리 서로 모순되지 않는다
- [x] 수치 기준(시간, 개수, 크기)이 필요한 AC에는 값이 있다 (해당 AC 없음)

## 5. 범위

### 포함

- 클라우드 자원 탭
- 모든 클라우드 플랫폼(AWS, K8s, vSphere, NCP, OpenStack, Contrabass 등)
- 업무 라벨 식별 정보 표시 (화면, 공통 컴포넌트 기준)
- 업무 라벨 기준 조회·필터링 (백엔드 기능 및 화면)
- 업무 라벨 미할당 자원 조회 (백엔드 기능만)
- 챗봇의 `/api/inventory` 하위 API에 대한 업무 라벨 할당 자원만 노출
- dev 환경 구현 후 prd 환경 적용

### 제외

- 권한 모델 통합
- 업무 라벨 미할당 자원 조회 화면
- `/api/inventory` 하위 외의 챗봇 호출 API

## 6. 가정

- 두 권한 체계(클라우드 플랫폼 권한, 업무 라벨 권한)는 모두 기존대로 유지된다.
- 업무 라벨 표시에 사용할 공통 컴포넌트가 이미 존재한다.
- 대상 플랫폼은 CMP가 지원하는 모든 플랫폼이다. 목록의 6개는 예시이며, 기술문서 단계에서 실제 지원 플랫폼 목록을 확정한다.

## 7. 비기능 요구사항 (초안)

- 권한이 없는 자원은 어떤 경로(화면, API, 챗봇)로도 노출되지 않아야 한다.
- (성능, 접근성, 운영 요건은 필요 시 추가)

## 8. 기술 영향

### 백엔드 (BE)

- API 추가·변경: 영향 큼. `/api/inventory` 하위 조회 API에 업무 라벨 식별 정보 제공, 업무 라벨 기준 필터링(OR), 미할당 조회, 챗봇 조회 시 라벨 할당 자원만 반환 (세부 항목은 기술문서에서 검토)
- 상태·전이 규칙 변경: 확인 필요
- 권한·역할 영향: 권한 모델 통합은 범위 밖. 기존 두 권한을 모두 존중하는 조회 동작 검토 필요

### 프론트엔드 (FE)

- 화면·흐름 추가·변경: 영향 큼. 클라우드 자원 탭 등에서 업무 라벨 표시(공통 컴포넌트) 및 필터 UI. 미할당 조회 화면은 없음
- 상태 표시·오류 처리: 확인 필요
